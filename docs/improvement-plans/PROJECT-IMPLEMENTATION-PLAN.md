# プロジェクト全体の改善実装計画

作成日: 2026-09-17
対象: Python Web / ブラウザ / manual-maker-workers / CI
状態: 実装開始、段階ごとに検証する

## 目的と作業規約

先行レビューの9案を実装する。各小ステップは「現行確認 → 回帰テストの追加 → 実装 → 対象テスト → 型・静的検査 → 結果記録」の順で進める。検証失敗は原因を切り分け、当該変更が原因なら修正してから次に進む。未実行・環境依存の検証を成功と記録しない。

- 既存の未コミット変更と並行更新を保持する。変更直前に対象を再読する。
- コミット・プッシュ・本番デプロイ・既存データ削除は実行しない。
- 認証方式、既存データの所有者、保存日数、稼働中のデプロイ構成を推測しない。
- APIの破壊的変更は互換経路とクライアント移行を先に用意する。
- テストでは外部AIや実クラウドストレージを呼ばず、モックとローカル環境を使う。
- 完了判定は実装の存在ではなく、実際の呼び出し経路と失敗時の動作を含める。

## 現行の再確認結果

- `manual-maker-workers` は Hono / Zod / Vitest / TypeScript。型検査は `npm run typecheck`、テストは `npm test`。
- 同パッケージの `build` は現在 `wrangler build`。CIは `wrangler deploy --dry-run` を使用しており、コマンドを統一する。
- `.github/workflows/workers-contracts.yml` が既に存在する。Node 22.13.1、ロックファイルによる導入、型検査、全テスト、ドライランビルドを実施する。以前の「新WorkersにCIがない」という判断は現状には適用しない。
- 旧 `.github/workflows/ci-cd.yml` は別の `manual_processor/workers` を検証・デプロイする。新Workersへ無条件に付け替えると配備対象を変えるため、先に利用構成を確認する。
- 新WorkersのKV IDはプレースホルダー。旧Workersディレクトリには `wrangler.toml` が見つからない。ローカルビルド成功は配備可能性を保証しない。
- Workers専用lintコマンドは未定義。型検査をlintと呼ばない。採用コマンドを確認する。
- Python既存CIには `python -m flake8 src/ config/ --count --select=E9,F63,F7,F82 --show-source --statistics` と `python -m pytest tests/ -v --cov=src --cov=config --cov-report=xml --cov-report=term` がある。
- 直前のWorkers検証は型検査成功、23ファイル160テスト成功。ただし各ステップでは改めて検証する。

## S1: CIとビルドの整合化

### S1.1 非デプロイのビルド経路を統一

対象: `manual-maker-workers/package.json`、`.github/workflows/workers-contracts.yml`。

1. `build` をローカルWranglerによる `deploy --dry-run --outdir dist-ci` に統一する。
2. CIは `npm run build` を使い、ローカルと同じコマンドを実行する。
3. CIが生成したバンドルをコミットSHA付き成果物として保存する。空の成果物を成功扱いしない。成果物に秘密情報や実行環境の状態を含めない。
4. Nodeバージョンを既存CIと揃えて検証する。
5. 型検査、全テスト、ビルド、Workflow YAMLの構文・構造チェックを実行する。

完了条件: 同一のビルドコマンドがローカルとCIで使われる。型検査・全テスト・ドライランが成功する。成果物保存がビルド成功に従属する。

### S1.2 デプロイ構成とゲートの統一

実配備の確認後に実施する。旧構成が現役なら旧構成の依存・ビルド・テストを修復し、新構成が本番なら新構成の検証成果物を配備対象にする。両方維持する場合は別ジョブと明示的な設定で分離する。

確認項目: Pages/Queue/Edgeの利用有無、Workersの実名、環境別binding、既存GitHub Environment、ブランチ保護、手動配備の必要性。

検証: PRとpushのパス条件、手動配備のneeds、失敗時の配備停止、プレビューでのbinding検査。リモート配備は別途承認が必要。

戻し方: 変更したビルド・Workflow部分のみを戻す。旧構成や実データは削除しない。

## S2: 認証と所有者チェック

対象: `src/app.ts`、`src/lib/types.ts`、各Workersルート、Python Webとブラウザの認証接点。

1. Cloudflare Accessまたは既存OIDC等、利用する認証方式を確認する。独自の未検証JWT検証器は作らない。
2. 利用者・所有者型と共通権限判定を用意する。信頼できないヘッダーだけで所有者を決定しない。
3. 新規データに所有者を付与し、既存の所有者不明データは明示した移行方式に従う。
4. 一覧、取得、変更、削除、WebSocket、AI利用の順に接続する。
5. ブラウザのログイン切れ表示、CORS、Cookie利用時のCSRF対策を認証方式に合わせる。

検証: 未認証、権限不足、同一所有者、別所有者、期限切れ、WebSocket接続、既存データ。権限判定を通らないストレージ参照がないことを確認する。

完了条件: 利用者間のデータ混在がなく、保護漏れのない回帰テストがある。移行前後のアクセス方針が明記される。

## S3: 完全成功・部分成功・失敗

対象: `manual_processor/src/processor/processor.py`、Python結果型、Workersスキーマ、UI結果表示。

1. `completed / partial / failed` とページ別・成果物別状態を定義する。
2. 既存 `success` の互換性を調べ、新フィールドを追加する段階と成功判定を変更する段階を分ける。
3. OCRの代替文字列だけでなく、失敗ページを構造化して返す。
4. 必須出力と任意出力を区別して最終状態を決定する。
5. 部分成功では警告と利用可能な成果物だけを表示する。

検証: 全成功、OCR一部失敗、全ページ失敗、必須出力失敗、任意出力失敗、キャンセル。正常レスポンスとエラーレスポンスの契約を検証する。

完了条件: 欠落成果物がある結果を無条件に完全成功と表示しない。既存クライアントの移行テストが成功する。

## S4: ジョブ単位のフロントエンド

対象: `manual_processor/src/web/static/js/app.js`、`manual_processor/functions/static/js/app.js`。

1. 二つの配布先と生成・複製関係を確認する。
2. 選択世代番号、固定のfileId/jobId、接続オブジェクトをジョブ状態にまとめる。
3. 古い要求をAbortControllerで中止し、中止できない応答も世代番号で無視する。
4. ダウンロードハンドラーは表示結果の固定IDを参照する。
5. `uploading/queued/processing/completed/partial/failed/cancelled` の表示を契約に合わせる。
6. WebSocketの再接続と上限付き状態照会を追加し、接続消失を処理完了とみなさない。

検証: 逆順アップロード、処理中のファイル切替、連打、古いWebSocket通知、再接続、アプリケーション失敗、成功成果物のダウンロード。

完了条件: 表示結果とダウンロード対象が一致する。HTTP成功だけで完了表示しない。

## S5: Pythonジョブ実行基盤

対象: `manual_processor/src/web/app.py`、既存オーケストレーター、設定、進捗・キャンセル機構。

1. 共有設定のリクエスト単位変更をやめ、ジョブ用スナップショットを生成する。
2. 既存の実行基盤を優先利用し、待機数・実行数を制限する。単純なasync関数化だけで同期処理を非同期化したとみなさない。
3. 状態を永続化し、起動時に中断ジョブを検出する。自動再実行は冪等性の確認後に有効化する。
4. 開始、状態照会、進捗、キャンセルのAPIを接続する。
5. S4対応後に202応答へ移行する。旧同期APIの互換方針を先に決める。

検証: 処理中のhealth応答、設定の分離、キュー満杯、例外、キャンセル、再起動、二重開始、複数ワーカーでの状態参照。

完了条件: イベントループを長時間占有しない。進捗と終端状態が永続化され、再起動後に中断を把握できる。

## S6: Durable Objectの進捗整合性

対象: `manual-maker-workers/src/lib/progress-engine.ts`、`src/routes/process.ts`、スキーマ、移行テスト。

1. 実行ID・更新番号と状態遷移表を定義する。
2. DO内で現在値の読み取り、更新可否の検証、永続化、通知を順に処理する。
3. 保存失敗は成功応答にせず、通知も確定状態のみとする。
4. フォールバックの更新とDO復旧時の競合解決を実行ID・版番号で規定する。
5. 再接続時は最新の確定状態を送信する。

検証: 順序逆転、重複通知、前回実行の更新、終端後更新、保存失敗、DO停止、復旧、通知失敗。

完了条件: 古い更新で状態が巻き戻らない。メモリ状態と永続状態の不一致を成功として扱わない。

## S7: 入力から出力までの資源制限

対象: `manual_processor/src/pdf_processor.py`、OCRパイプライン、Workers validation/body-limit/upload。

1. Pythonの全ページ画像リストを遅延生成または上限付きバッチへ変更する。
2. PDFハンドル・画像・一時ファイルをfinallyで解放する。
3. Workersの本文解析前に実際の受信バイト数を制限する。Content-Lengthだけに依存しない。
4. 容量、ページ数、画素数、同時実行数の上限を設定化する。PDFの内容検証を追加する。

検証: 境界サイズ、ヘッダーなし本文、壊れたPDF、多ページ、高解像度、途中例外、キャンセル。代表入力でピークメモリを測定し、採用する予算値を記録する。

完了条件: 大容量入力で全ページを同時保持しない。上限超過が明確に拒否され、資源が解放される。

## S8: 外部AI通信の共通化

対象: `src/lib/http-client.ts`、`external-api.ts`、`circuit-breaker.ts`、Gemini/Visionルート。

1. 既存の実利用経路と未使用ラッパーを整理する。
2. 接続認証、要求タイムアウト、全試行の期限、キャンセルを共通処理にする。
3. Retry-After、再試行対象、POST再送の課金・重複リスクを踏まえて制限する。
4. サーキットブレーカーの共有範囲を明示する。
5. キャッシュは所有者、入力ハッシュ、モデル、設定、操作を区別する。異なる入力の結果を障害時に返さない。
6. 通常JSONとストリーミングを分離し、切断時の上流キャンセルを実装する。

検証: 通常応答、429、5xx、認証失敗、タイムアウト、中止、開放・回復、別入力キャッシュ、ストリーム途中失敗。外部APIはモックする。

完了条件: 応答とエラー契約が維持され、再試行に上限があり、機密情報がログへ出ない。

## S9: 保存期限と削除の一貫性

対象: Pythonジョブ管理、Workers upload/results、R2/KV複製、scheduled、キャッシュ。

1. 保存日数と原本のみ削除・案件全体削除の意味を確認する。既存文書へ即座に期限を付けない。
2. 案件に関連する原本、生成物、進捗、キャッシュ、複製を追跡する。
3. 削除予約、削除中、再試行待ち、完了を記録する。
4. 利用者削除と定期削除を共通化し、冪等に実行する。
5. 削除墓標とバックアップの保持方針を定義し、復元による復活を防ぐ。

検証: 二重削除、一部ストレージ停止、復旧後再実行、複製遅延、期限境界、バックアップ復元、削除中のアクセス。

完了条件: 全関連データの削除を追跡できる。部分失敗が無視されず、所有者権限に従って削除される。
